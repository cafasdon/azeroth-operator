# ADR006: Player-applied game operations

Status: implementation in progress,2026-11-03. Supersedes the project's blanket read-only implementation target, not the existing prohibitions on input automation, protected-action bypass, autonomous gameplay or arbitrary Lua execution. User explicitly requested the fullest policy-compliant operational coverage.

The MCP must produce concrete, versioned operations; the addon must execute supported game APIs following player review/apply where required. Draft generation alone is not completion. First delivery is macro create/edit/delete and account/character scope moves. Action-bar placement is a separate operation and is not implied by moving a macro between scopes.

Transport starts with a bounded data import through an addon text box. No loadstring or executable external Lua. A review displays operation, source scope/expected fields, destination and requested fields before a player applies one operation. Bind client family/build/interface and character/realm to the operation and check again at apply. The addon records an operation ID and outcome; no timer/login execution, automatic combat retry or ambiguous-write replay. Persisted SavedVariables are a reload/logout checkpoint, not crash-durable transactional storage; UI must not promise exactly-once execution across crashes.

MacroOperations.lua is an uninstalled execution module. It uses CreateMacro/EditMacro/DeleteMacro and readback, never RunMacro. Combat/interface/family, exact preimage and scope capacity checks precede writes. Scope move is copy then delete after destination verification; it may leave two copies, explicitly reported. Macro indices may renumber; resolve source again after creation. A failure after an API attempt is outcome-unknown until reconciled, never automatic retry. Current fixtures use fake APIs and do not prove live compatibility.

API evidence: Blizzard's mirrored [MacroIconSelector source](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_MacroUI/Blizzard_MacroIconSelector.lua) uses CreateMacro and EditMacro from its OkayButton handler. This confirms the API usage pattern; it is not approval for autonomous remote game control.

Changing input or closing the window invalidates review. These modules are not yet in distribution packages. The operation digest is a replay identifier, not a signature or authentication claim. SavedVariables receipts remain bounded to 128 attempts; there is no automatic purge or retry.

Concrete integration issue before installation: declaring `AzerothOperatorOperations` as a SavedVariable emits another assignment in the same file. The existing Rust importer accepts only one quoted export assignment, so the new file would be rejected after reload. The importer and Python reference must gain a bounded, non-executing receipt-data contract, with real SavedVariables-shaped fixtures and deployed importer/companion compatibility before installation. The package fixture currently exercises loaded Lua and capture, not WoW's SavedVariables serialisation; its success does not resolve this issue.

Receipt format resolution: `AzerothOperatorOperations` is now a string of `operation_id:status:kind;` records, at most 128 records and 16 KiB. Only fixed status/kind enums and lowercase SHA256 IDs are accepted; duplicate IDs fail. Lua parses this string before applying and saves `outcome_unknown` before the mutation call, then the observed result. SavedVariables still checkpoint only on reload/logout. The Rust importer accepts precisely the export and optional receipt string assignments in either order, validates all receipt records, and imports the original snapshot. Tests cover legacy input, both assignment orders, duplicate records/assignments and executable suffix rejection. The Python reference only handles JSON snapshots and does not parse SavedVariables; no Python Lua parser is needed. Receipt data is not yet exposed through hosted snapshots. The newly built local companion must be installed before this addon; remote upload currently receives decoded JSON, not SavedVariables. Full source verification passed after this change.

Receipt readback source checkpoint: the addon now captures `operation_receipts` into the snapshot. Rust accepts at most 128 lowercase SHA256 keys with exactly `status` and `kind`, each checked against fixed enums. The existing `inspect_snapshot` tool reads this section; both Rust and reference MCP protocol tests preserve `outcome_unknown`. The actual Lua producer test captures a persisted receipt and validates it through the Rust importer, including malformed-section rejection. Full source verification passed. This is captured historical evidence, not a fresh game-state reconciliation or proof of crash durability. Receipt IDs bind the original operation and snapshot; preparing a new operation against a new snapshot produces a different ID, so the ID guard must not be described as preventing all semantically equivalent retries. Deploy both hosted reader and importer with this additive schema before enabling exports from the new addon.
